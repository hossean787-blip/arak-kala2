# معماری فنی اراک کالا — نسخه طراحی و نمونه اجرایی 0.1.0-alpha

## هدف و مرز پروژه
اراک کالا یک فروشگاه اینترنتی **تک‌فروشنده** است؛ مشتریان فقط از وب خرید می‌کنند و «اپ اراک کالا مدیر» تنها برای حساب مدیر اصلی است. هیچ ثبت‌نام عمومی فروشنده و هیچ مدل مارکت‌پلیس وجود ندارد. پروژه از سپاس، دتا، سورا و دیگر پروژه‌ها جدا نگه داشته می‌شود.

## قرارداد طراحی
- برند: `ARAK / KALA`، لوگوتایپ سیاه، پس‌زمینه روشن، نقطه گرم نارنجی.
- رابط فارسی راست‌چین، فونت وب Vazirmatn از Google Fonts با جایگزین Tahoma در حالت آفلاین.
- هدر کوچک چسبان، هیروی تایپوگرافی، فرم جست‌وجو و فیلتر، کارت کالا با نسبت تصویر 1:1 و `object-fit: contain` برای جلوگیری از بریدگی تصویر کالا.
- انیمیشن‌های کم‌حجم و اختیاری؛ رعایت `prefers-reduced-motion`، چیدمان موبایل دو ستونه.
- **بدون محصول نمونه:** فروشگاه به طور پیش‌فرض خالی است تا مدیر محصولات واقعی را بارگذاری کند.

## معماری نسخه اولِ قابل اجرا در بسته
- **Front-end وب:** HTML + CSS + JavaScript بدون build؛ SPA سبک، واکنش‌گرا و مستقل از فریم‌ورک.
- **API نمونه:** Python 3.8+ و `http.server`، بدون کتابخانه خارجی.
- **بانک نمونه:** SQLite تراکنشی، WAL، کلید خارجی، پارامترگذاری SQL، تراکنش `BEGIN IMMEDIATE` برای کسر/بازگشت موجودی.
- **اپ اندروید:** Kotlin، Jetpack Compose، درخواست HTTP با `HttpURLConnection`؛ فقط حسابی با `role=admin` مجاز است.
- **توکن:** تصادفی، عمر ۱۲ ساعت، هش‌شده در دیتابیس، در وب داخل `sessionStorage` و در اپ فعلاً فقط حافظه؛ برای انتشار باید مدل نشست و امنیت نهایی شود.
- **تصاویر:** آپلود فقط توسط مدیر، حداکثر ۲ مگابایت در هر فایل، JPEG/PNG/WebP؛ فایل در `/uploads/` با نام تصادفی نگهداری می‌شود.

## ساختار دامنه و سرویس در نسخه تجاری
در حالت استقرار پیشنهادی، دامنه موجود کاربر به همین شبکه متصل می‌شود:
- `https://<DOMAIN>/`: سایت مشتریان.
- `https://<DOMAIN>/api/`: API نسخه‌بندی‌شده (`/api/v1` پس از آماده‌سازی برای انتشار).
- تصاویر در Object Storage خصوصی/عمومی کنترل‌شده پشت CDN و مسیر media؛ به‌جای فایل محلی روی یک سرور.

**نسخه تجاری پیشنهادی:** سرویس Python با FastAPI + PostgreSQL، Object Storage سازگار S3، reverse proxy (Nginx یا Caddy) و HTTPS، برنامه پشتیبان‌گیری روزانه. APIهای این نمونه می‌توانند بدون تغییر تجربه کاربری به این معماری منتقل شوند. انتقال باید با migration و آزمون یکپارچگی انجام شود؛ دیتابیس SQLite نمونه را مستقیماً محصول تجاری تلقی نکنید.

## مدل داده
| جدول | فیلدهای مهم | وضعیت در بسته |
|---|---|---|
| users | id, email, full_name, phone, role, password_hash | پیاده‌سازی شده |
| sessions | token_hash, user_id, expires_at | پیاده‌سازی شده |
| products | id, name, category, description, price, stock, active, images | پیاده‌سازی شده |
| orders | id, user_id, full_name, phone, address, total, status | پیاده‌سازی شده |
| order_items | order_id, product_id, unit_price, quantity | پیاده‌سازی شده |
| product_variants | color, size, sku, stock | طراحی برای مرحله بعد؛ هنوز اجرا نشده |
| payment_transactions | authority, order_id, amount, verified_at | نیازمند اتصال درگاه؛ اجرا نشده |
| addresses / shipping | address, postal_code, method, tracking_code | تکمیل در مرحله بعد |
| audit_logs | actor, action, timestamp, before, after | برای نسخه تجاری ضروری |

**واحد پول API:** عدد صحیح تومان؛ استفاده از عدد اعشاری شناور برای قیمت ممنوع. تصاویر محصول فعلاً به‌صورت آرایه JSON در ردیف کالا نگهداری می‌شوند؛ در نسخه تجاری بهتر است جدول جداگانه داشته باشند.

## گردش کار واقعی
1. مدیر از اپ اندروید با ایمیل ثبت‌شده و رمز انتخابی وارد می‌شود.
2. عکس از Photo Picker انتخاب و فشرده می‌شود. اپ `POST /api/admin/images` می‌زند و آدرس تصویر را می‌گیرد.
3. اپ محصول را با مشخصات و آدرس تصاویر در `POST /api/admin/products` ثبت می‌کند.
4. سایت با `GET /api/products` کالا را نمایش می‌دهد. با همان API و دیتابیس، همگام‌سازی رخ می‌دهد؛ نیاز به ارسال دستی دوباره نیست.
5. مشتری حساب می‌سازد، وارد می‌شود و سبد خرید را ثبت می‌کند. سرور قیمت و موجودی را مجدداً تأیید کرده و سفارش آزمایشی ایجاد می‌کند.
6. مدیر در اپ سفارش را تأیید یا لغو می‌کند. لغو سفارش در وضعیت مجاز موجودی را بازمی‌گرداند.

**مهم:** پرداخت آنلاین وجود ندارد. سفارش‌ها فعلاً برای تست فقط ثبت و به‌صورت دستی مدیریت می‌شوند. فرایند پرداخت واقعی، کنترل انقضای رزرو موجودی و تأییدیه پرداخت سمت سرور باید قبل از عرضه عمومی اضافه شود.

## الزامات امنیت و عملیاتی پیش از انتشار
- HTTPS اجباری + گواهی معتبر و عدم پذیرش HTTP در نسخه Release اندروید.
- افزودن rate limiting، قفل موقت/ضد حدس رمز، reset password امن، احراز هویت دومرحله‌ای مدیر.
- ذخیره امن توکن در اپ (Android Keystore / ذخیره‌سازی رمزنگاری‌شده)، چرخه refresh/revoke، اعتبارسنجی کاربر در هر API.
- پاکسازی و رمزگذاری داده حساس در گزارش‌ها؛ تکمیل سیاست حریم خصوصی و حداقل دسترسی.
- اعتبارسنجی محتوایی و بازکدگذاری تصویر، حذف EXIF، محدودیت تعداد و جلوگیری از آپلود مخرب.
- پرداخت از درگاه ایرانی با اعتبارسنجی نهایی callback یا استعلام از درگاه **روی سرور**؛ هیچ شماره سفارش صرفاً با callback مرورگر «پرداخت‌شده» نشود.
- PostgreSQL و مهاجرت Schema، بکاپ و تست بازیابی، لاگ ممیزی، پایش سلامت، تست بار و تست مرورگر واقعی.
- سازوکار هلد موجودی برای سفارش پرداخت‌نشده و آزادسازی خودکار پس از timeout، جلوگیری از overselling.

## وضعیت مراحل
- **تکمیل و آزموده‌شده (فقط محدوده نمونه):** API ورود/ثبت‌نام، تفکیک دسترسی، آپلود تصویر، محصول، جست‌وجو، کسر/بازگشت موجودی، ثبت سفارش و حذف منطقی؛ آزمون integration با Python.
- **پیاده‌سازی‌شده اما آزمون مرورگر کامل نشده:** UI مشتریان، ریسپانسیو CSS، جست‌وجو، سبد خرید، فرم ورود و ثبت سفارش در مرورگر.
- **متوقف به‌دلیل مانع آزمون:** ساخت APK و اجرای اندروید (Android SDK و Gradle Wrapper در محیط فعلی موجود نیستند). سورس اولیه ارائه شده است.
- **انجام‌نشده:** اتصال دامنه، درگاه بانکی، پیامک، انواع رنگ/سایز، روش ارسال، گزارش مالی قطعی، استقرار تجاری و تست بار.
